# Forge 2.0 (design)

Date: 2026-08-12  
Status: approved for planning  
Approach: Forgefile-centric control plane

## Problem

Forge 1.x hardcodes a `build.sh` → `test.sh` → `deploy.sh` contract, assumes GitHub as the only remote, runs Cursor agents as child processes inside the Forge app container, and has no first-class multi-deploy, service directory, or downloadable artifact model. Repos cannot declare maintenance scripts, discrete deployments, ports, or artifacts in one place. Agents share Forge’s Docker privileges and cannot be cleanly isolated or killed as unresponsive units.

## Goals

1. **Forgefile (required)** — YAML manifest at repo root declaring scripts, named deployments (ports/subdomains), artifacts, and agent bootstrap hints. Thorough documentation + fully annotated template so other repos can adopt without reading Forge source.
2. **Agent containers** — every agent session runs in its own container; clones from Forge git; no Docker socket; talks to Forge via Ops; Forge kills on heartbeat miss, idle, or wall-clock max.
3. **Forge as primary git host** — HTTP + SSH; UI can create entirely new projects; one-shot GitHub import into Forge bare repos.
4. **Service directory** — command-center registry of declared + observed ports/URLs per deploy target, with basic monitoring and Caddy route scaffolding.
5. **Artifacts** — declare + build via Forgefile; store on disk (v1) with storage-driver interface ready for S3; distribute via API + UI download.

## Non-goals (v1)

- Job-queue platform rewrite of all Forge work.
- Dual GitHub+Forge ongoing sync (mirror-out optional later; import is one-shot).
- Agents retaining Docker/Podman access.
- Fancy UI redesign (functionality only; reuse existing command center / project surfaces).
- Removing Ops auth or global CI tokens.

## Decisions (locked)

| Topic | Choice |
|-------|--------|
| Architecture | Forgefile-centric control plane |
| Missing Forgefile | Required; offer to spin up an agent to create one |
| Format | YAML (`Forgefile`; alias `forgefile.yml`) |
| Git | Forge is primary origin; GitHub import once |
| Existing GitHub projects | Import into bare store; Forge becomes origin |
| Agent power | No Docker; git + Ops API only |
| Deployments | Named targets with distinct ports/subdomains |
| Secrets | Hybrid: inject git + Ops token; other secrets via audited Ops request |
| Agent kill policy | Heartbeat miss + idle timeout + wall-clock max |
| Artifacts storage | Disk on Forge volume; API shaped for S3 later |
| Git transport | Smart HTTP + SSH |
| Service directory | Declared + observed ports; basic health monitoring; Caddy route scaffolding for public+subdomain |
| Forgefile docs | Deep author guide + fully annotated template (every option; unused commented out) |
| Implementation order | Forgefile → service directory → artifacts → agent containers → git server |

## Interim vs final git

Phases 1–4 may still clone from GitHub for existing projects so work is not blocked on the git server. **Forgefile is still required** in those phases. Phase 5 switches origin to Forge and adds create-project + import.

## 1. Forgefile

### Filenames

- Preferred: `Forgefile` (YAML) at repo root
- Alias: `forgefile.yml`
- If both exist: prefer `Forgefile`; treat mismatch as validation error if contents differ

### Required

After clone/checkout/import, pipeline actions (script run, deploy, auto-watch deploy, artifact build) **fail closed** without a valid Forgefile. UI/Ops show a clear error and a **“Create Forgefile with agent”** CTA that starts a restricted bootstrap session (author + commit Forgefile only until valid).

### Illustrative schema (`version: 1`)

```yaml
version: 1

project:
  name: my-app
  # compose_slug: my-app   # optional override

scripts:
  build:
    run: ./build.sh
    description: Compile and image-build
  test:
    run: ./test.sh
  migrate:
    run: ./scripts/migrate.sh
    description: Maintenance; runnable from UI/Ops

deployments:
  web:
    description: Public web app
    auto_deploy: false       # default false; true = watcher deploys this target on new commits
    scripts:
      build: build          # reference scripts.* or inline run
      test: test
      deploy: ./deploy.sh --target web
      teardown: ./teardown.sh --target web
    ports:
      - name: http
        port: 8080
        public: true
        # health:            # basic monitoring
        #   path: /api/health
        #   interval_seconds: 30
    subdomain: web           # web.<forge-domain> when Caddy configured
  worker:
    auto_deploy: false
    scripts:
      deploy: ./deploy.sh --target worker
    ports:
      - name: metrics
        port: 9090
        public: false

artifacts:
  linux-amd64:
    description: CLI binary
    build: ./scripts/build-artifact.sh linux-amd64
    path: dist/my-app-linux-amd64
    # content_type: application/octet-stream

agent:
  packages: []               # optional install hints for agent container
```

### Semantics

- **Scripts** — named; runnable from UI/Ops (`POST …/scripts/{name}/run`). Pipeline or maintenance.
- **Deployments** — discrete named targets; each has ports, optional subdomain, script bindings. Deploy/teardown always name a target.
- **Artifacts** — build command + output path for registry/download.
- **Agent** — non-secret bootstrap hints only.
- Script env/args from Forge: `--project-name`, `--host-port` / per-deployment port env, `FORGE_DEPLOYMENT=<name>`.

### Pickup on change (required)

Any commit that changes the Forgefile is **re-validated and re-projected** into SQLite (scripts, deploy targets, ports, artifacts). Stale projections reconcile before the next script/deploy. UI indicates when the live model lags HEAD. Git `post-receive` (phase 5) and watcher/pull (interim) both trigger pickup.

### Documentation deliverables (required, thorough)

1. **`docs/Forgefile.md`** — full author guide: concepts, validation rules, multi-deploy, ports/Caddy, artifacts, agent hints, Ops/UI how-to, migration from bare `build.sh`/`test.sh`/`deploy.sh`, examples.
2. **`docs/forgefile.template.yml`** — **every** potential option present; unused options **commented out** with short explanations. Canonical starter copied into new repos and used by the bootstrap agent.
3. Updates to `README.md`, `AGENTS.md`, and Ops catalog.

## 2. Control plane & data model

Forge remains the privileged orchestrator (Docker/Podman, Caddy, secrets). Forgefile is projected into DB so UI/Ops do not re-parse YAML on every click.

### Conceptual tables

| Table | Role |
|-------|------|
| `git_repositories` | Bare repo id, slug, disk path, import source, default branch |
| `projects` | Links to git repo; display name; enabled; loses GitHub-only identity |
| `deploy_targets` | Per project: name, subdomain, ports JSON, script bindings, compose slug |
| `service_directory` | Declared + observed endpoints; monitoring fields; Caddy route status |
| `artifacts` / `artifact_builds` | Declarations + build runs (status, sha, storage key, size) |
| `secrets` | Project/global named secrets (encrypted at rest); request audit |
| `agent_containers` | Container id, session id, heartbeats, activity, deadlines |

### Execution

- Script run, deploy, artifact build = **Forge-side privileged jobs** (not in agent containers).
- Watcher/auto-deploy: after Forgefile validation, enqueue only targets with `auto_deploy: true` (default `false`).

## 3. Agent containers

### Lifecycle

1. Start session → Forge creates container from agent image.
2. Clone branch from **Forge git** (HTTP + session token). Interim: GitHub clone still allowed until phase 5.
3. Inject bootstrap only: Ops base URL, session Ops token, git credentials, heartbeat config.
4. Entrypoint may install `agent.packages`, then run Cursor agent CLI in the worktree.
5. Agent uses git + Ops only (**no Docker socket**).
6. Heartbeats + activity (Ops calls, streamed events) recorded on Forge.
7. Kill container when: heartbeat misses threshold, idle timeout, or wall-clock max → session `failed`, container removed.

### Communication

- Agent → Forge: Ops API (scripts, deploy, secrets request, artifacts, heartbeat, events).
- Prefer **agent posts events to Forge** (UI does not depend on Docker logs).
- Forge → Agent: kill container; optional soft-cancel later.

### Secrets (hybrid)

- Always inject: git credentials for Forge origin, `FORGE_OPS_API_TOKEN`, `FORGE_OPS_API_BASE`, heartbeat settings.
- All other secrets: agent requests by name via Ops; Forge audits allow/deny; never mount the full secret store.

### Missing / invalid Forgefile

Bootstrap mode: fixed system prompt; Ops restricted to writing/committing a valid Forgefile (and reading repo) until validation passes.

## 4. Git server

### Storage

Bare repos under `/data/git/<slug>.git` (persistent volume).

### Create project (UI)

1. Name + slug + default branch.
2. Create bare repo; seed initial commit (README + **annotated Forgefile template**).
3. Register `git_repositories` + `projects`.
4. Show HTTPS + SSH clone URLs.

### Import from GitHub

One-shot clone into bare store; Forge becomes origin; record `imported_from`. No ongoing dual-remote requirement in v1.

### Access

- **Smart HTTP** — session cookie (UI) or bearer/token (agents/CI).
- **SSH** — `git@<host>:<slug>.git`; user/deploy keys in Global settings.
- Same authz model for read/write.

### Working copies

- Privileged jobs: checkouts under `/data/repos/…` (or ephemeral) from Forge origin.
- Agents: fresh clone per session; push to Forge.

### Hooks

`post-receive` notifies Forge → Forgefile pickup if changed; wake watcher for auto-deploy targets.

## 5. Service directory

### Purpose

Command-center section listing every known service endpoint across projects. Each deploy target also shows its own port table on the project page.

### Sources (merged)

1. **Declared** — Forgefile `deployments.*.ports` + `subdomain` (on pickup).
2. **Observed** — post-deploy container/port inspect + Caddy sync → bound port, URL, status.
3. Rows include: project, deploy target, port name, port, public?, subdomain/URL, status, last checked, deployment/commit when known.

### Basic monitoring

- Optional per-port `health` in Forgefile (`path`, `interval_seconds`, etc.).
- Forge probes public (and optionally private) endpoints on an interval.
- Directory shows up/down/unknown, last check time, last latency or error summary.
- Failures do not auto-redeploy in v1; they surface in UI/API only.

### Caddy scaffolding

- Public ports with subdomain → allocate/sync route via Caddy admin API (extend existing `caddy-config` / `project-routing` patterns).
- Private ports: directory-only, no public route.
- Sync failure: directory shows route error; do not claim public URL is live.
- Port reservation: two targets cannot claim the same host port.

### Stale data

- Forgefile drops a port → projection removes row.
- Container gone → status `down`; row remains until Forgefile/teardown removes target.

### API

`GET /api/ops/services` (+ dashboard equivalent).

---

## 6. Artifacts

### Declare

Forgefile `artifacts.<name>`: description, build command, output `path`, optional content-type.

### Build

Forge privileged job in a checkout for commit/branch; store result via storage driver.

### Storage

- **v1:** `/data/artifacts/{projectId}/{artifactName}/{buildId}/…`
- **Interface:** `put` / `get` / `delete` / `signedDownload` — disk first; S3-compatible later without API break.
- **Retention:** last N builds per artifact name (default e.g. 10); manual delete.

### Distribution

- UI download button on project (optional command-center entry).
- Ops/API: build, list builds, authenticated download.
- Agents may request builds; download via authorized URL/token only — no raw FS.

---

## 7. Rollout, testing, errors

### Implementation order

1. Forgefile parse/validate + projection + **change pickup** + docs + annotated template  
2. Service directory + basic monitoring + Caddy scaffolding + multi-deploy targets  
3. Artifacts (disk driver + UI/API)  
4. Agent containers (heartbeat/idle/wall-clock, Ops-only, hybrid secrets)  
5. Git server (HTTP+SSH, create project, GitHub import)

### Migration

- Existing projects: block pipeline until valid Forgefile; CTA for agent-author or template.
- GitHub → Forge import when git server lands.
- Interim GitHub clone allowed for phases 1–4 with Forgefile required.

### Testing

- Unit: schema/validate, projection/reconcile on Forgefile change, port conflicts, artifact retention, heartbeat kill logic.
- Integration: Ops script run, deploy target → directory + Caddy scaffold, artifact build/download.
- Agent container: spawn, heartbeat miss → kill, secrets allow/deny audit.
- Git: create, push/pull HTTP (+ SSH if feasible), GitHub import.

### Error handling

| Case | Behavior |
|------|----------|
| Missing/invalid Forgefile | No deploy/script/artifact; offer agent bootstrap |
| Agent unresponsive | Kill container; session failed |
| Caddy sync failure | Directory shows route error; no fake public URL |
| Artifact build fail | Failed build row; no download |
| Port conflict | Reject projection / deploy with clear error |

## Relationship to current code

| Area today | 2.0 direction |
|------------|----------------|
| Hardcoded `build.sh`/`test.sh`/`deploy.sh` in `deployer.ts` | Drive from Forgefile scripts + deployment bindings |
| `projects.github_repo` + `github.ts` | `git_repositories` + Forge origin; GitHub import path |
| Agents in `agent-runner.ts` as child processes | Per-session containers; events/heartbeat via Ops |
| `host_port` / Caddy on project | Per **deploy target** ports + service directory + monitoring |
| `releases/*.json` image pins only | Keep image release pins; add file **artifacts** store |
| Ops session tokens (`fos.*`) | Keep; extend Ops for scripts, secrets request, heartbeat, services, artifacts |

## Open parameters (defaults for plan; tunable later)

| Parameter | Suggested default |
|-----------|-------------------|
| Heartbeat interval | 10s |
| Heartbeat miss threshold | 3 |
| Idle timeout | 30m |
| Wall-clock max session | 2h |
| Artifact retention N | 10 |
| Health check interval | 30s (or Forgefile override) |

These are implementation defaults, not blockers for planning.
