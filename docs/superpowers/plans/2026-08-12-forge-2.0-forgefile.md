# Forge 2.0 Plan 1 — Forgefile Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a YAML `Forgefile` the required contract for every project: parse/validate, project into SQLite, pick up on change, gate deploy/script runs, expose Ops/UI status + script runner, document thoroughly with an annotated template, and offer an agent CTA when missing/invalid.

**Architecture:** Add a pure parse/validate module + filesystem loader; persist a projection (`project_forgefiles` + `deploy_targets`); reconcile after every pull/checkout and whenever content hash changes; change `deployer` / Ops to read bindings from the projection instead of hardcoding `build.sh`/`test.sh`/`deploy.sh`. Missing or invalid Forgefile fails closed with a bootstrap-agent CTA.

**Tech Stack:** TypeScript, `yaml` package, Vitest, Drizzle/SQLite (`src/lib/db`), existing `deployer.ts` / Ops routes / agent session APIs, Next.js App Router.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-08-12-forge-2.0-design.md`
- Roadmap: `docs/superpowers/plans/2026-08-12-forge-2.0-roadmap.md`
- Filename: prefer `Forgefile`; alias `forgefile.yml`; if both exist and differ → validation error
- Forgefile **required** — no silent fallback to bare `build.sh`/`test.sh`/`deploy.sh`
- Missing/invalid → block pipeline; offer “Create Forgefile with agent”
- Pickup: any commit that changes Forgefile must re-validate and re-project before next script/deploy
- `auto_deploy` defaults to `false` per deploy target
- Docs: `docs/Forgefile.md` (thorough) + `docs/forgefile.template.yml` (every option; unused commented out)
- Out of scope for this plan: service directory UI/monitoring, Caddy scaffolding, artifacts store, agent containers, git server
- Never run Forge’s own `./deploy.sh` from agents; verify with `./build.sh --skip-install` and `./test.sh`
- Frequent commits after each green task

import { parseForgefileYaml } from "@/lib/forgefile-parse";

const MINIMAL = `
version: 1
project:
  name: demo
scripts:
  build:
    run: ./build.sh
deployments:
  web:
    scripts:
      build: build
      deploy: ./deploy.sh --target web

        port: 8080
        public: true

describe("parseForgefileYaml", () => {
  it("parses a minimal valid Forgefile", () => {

    expect(result.ok).toBe(true);
    if (!result.ok) return;
    expect(result.value.version).toBe(1);
    expect(result.value.project.name).toBe("demo");

    expect(result.value.deployments.web.ports[0]?.port).toBe(8080);

project:

deployments: {}

project:

    run: ./build.sh

  a:

      deploy: ./deploy.sh -t a

        public: true
  b:

    expect(result.ok).toBe(false);
    if (result.ok) return;
    expect(result.errors.some((e) => /port/i.test(e.message))).toBe(true);

Create `src/lib/forgefile-parse.ts` that:

1. `parse(source)` via `yaml` package
2. Requires `version === 1`, non-empty `project.name`, at least one deployment
3. Each deployment: `scripts.deploy` required (string); `auto_deploy` default `false`; `ports` default `[]`
4. Port entries: `name`, `port` (1–65535 int), `public` boolean default `false`
5. Script refs in `deployments.*.scripts.build|test` that are bare names must exist in `scripts`
6. Inline `run` strings (contain `/` or start with `.`) are allowed for deploy/teardown/build/test values
7. Cross-deployment: unique `port` numbers
8. Defaults: `artifacts: {}`, `agent: { packages: [] }`, `scripts: {}`

Helper for “is script ref vs inline”:

```ts
export function isInlineRun(value: string): boolean {
  return value.includes("/") || value.startsWith(".") || value.includes(" ");
}
```

When resolving later (Task 5+), refs look up `scripts[name].run`; inline values are used as-is.
